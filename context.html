Working past the context limit

Which ways of managing an AI’s memory actually helped?

Keep a small working context, and keep the originals searchable. That combination gave the strongest results on our long-history tests. A keeper handles the notes and archive outside the working agent, so the agent can concentrate on the task.

What helped on a long job?

The same model read a 240K-token history through a 32K working window, answering questions about facts, earlier values and rules stated at the start. Here is the first stream, with the same 39 questions for every approach.

A small desk, with the full history on file

Before old turns leave, the keeper saves them word for word and asks the model to refresh a short note: rules, current state and open work. It restores omitted rules and repeats them beside new questions. The model can search the originals whenever the note is not enough.

Follow the keeper step by step · How this differs from self-editing

The keeper runs inside the test program; the proxy puts that policy between an ordinary client and the model server. Each million-token result is one run. The proxy has not yet been tested under a real coding or research agent. What it missed and the original measurements.

Choose what the task needs to remember

  1. For a long, changing conversation: keep searchable originals, short working notes and protected rules. Keeper and archive results.
  2. For a ledger or repeated calculation: let code maintain the totals. Files and code finished the 121K ledger in 1.9 minutes with all answers correct. For prose, the model can submit quoted changes for code to apply. See both workflows.
  3. When the source fits comfortably: try supplying it together. Whole-history reading led on the 56-question chat-memory test. Compare with archive and summaries.

Summaries can work: they matched the archive on the smaller retention test, but took longer. A summary alone cannot recover a detail it omitted. Accuracy and time, side by side.
