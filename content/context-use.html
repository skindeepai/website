Keep a long task going with ctxkeeper. This free, public-domain proxy gives your AI agent a shorter working view: current notes, opening instructions and recent turns. Older messages stay on disk, word for word, for the model to search. Install it between your agent and an existing model server.

What it does

Think of a desk and a filing cabinet. The model works at a small desk: the opening instructions, a page of notes and the newest messages. Everything else goes into the cabinet, unchanged. Three things keep the desk useful:

  1. Notes, kept up to date. Every so often the model writes down only what changed: a new rule, a changed figure (with the working), a new open question. ctxkeeper checks the notes format and arithmetic it recognizes, and keeps rules already recorded in the notes. These checks do not prove that the notes are true.
  2. Search. The model gets one extra tool, recall, that searches the cabinet. ctxkeeper answers it itself; your agent never sees that step.
  3. Rule reminders. By default, rules recorded in the notes are repeated after new user messages. Instructions inside tool results need an optional matching rule (--recite-when). The model can still make mistakes.

The proxy changes the messages sent to the model. It manages Chat Completions requests from clients that keep sending their full history; see the client requirements. Follow the keeper step by step.

What it costs. The model writes its own notes on the same server, so nothing extra is loaded. In the million-token run about 15 of the 50 minutes went on writing notes and about 15 on reading (2.4M tokens for a 1M-token history); on the repair task notes took under a tenth of the time. A short view keeps every step fast, which is why the 200K window above took 228 minutes.

On one card. The same model on a single B70 with a 26K view fixed all 40 bugs, kept every rule and answered 7/7 in 21 minutes (two cards: 16).

Which model do I need?

The main task results on this page were measured on Qwen3.8-27B (FP8, served by vLLM on Intel Arc Pro B70 cards). A quick check on a second family, Gemma 4 26B (Q8, llama.cpp), passed the demo 4 of 4. Other models need checking with your task. They must call tools reliably, keep the notes format, and fit the configured working view plus their server’s overhead. The default view is 32,768 tokens, including the reply.

  • Let the model keep its own notes. A separate smaller keeper model, tried on a second card, was worse and slower (19 of 39 against 39/39 on the 240K test): it must read every turn afresh, while the main model re-reads its own cached view.
  • One card is enough: the repair task scored the same in 21 minutes (two cards: 16).
  • Turn the server’s prefix cache on: 91% of the notes calls’ prompt tokens came from the cache in the measured Qwen run.
  • With speculative decoding (MTP), keep the default in-line notes; background notes were correct but 8% slower there.
  • With the Qwen recipe, thinking can stay on for the agent’s turns; its notes calls disable thinking. The generic agent recipe does not set model-specific thinking options.

Not measured yet: other models’ quality through the proxy, and more than one conversation at a time. Window sizes and the speed numbers behind this advice are in Settings below.

Install and try stable 1.1.0

You need Python 3.10 or newer with pip and venv, or Docker for the proxy, and a running model server. ctxkeeper does not download or serve a model. The proxy and demo use Python’s standard library. The commands below use a local server at http://127.0.0.1:8000 that accepts Chat Completions and tool calls, with enough context for the default 32K view.

Python install

In a terminal on Linux or macOS:

python3 -m venv .venv-ctxkeeper
. .venv-ctxkeeper/bin/activate
R=https://github.com/steveseguin/b70-optimization-lab/releases/download/ctxkeeper-v1.1.0
python -m pip install "$R/ctxkeeper-1.1.0-py3-none-any.whl"
ctxkeeper --upstream http://127.0.0.1:8000 --recipe agent \
  --state-dir "$HOME/.local/share/ctxkeeper"

Replace the upstream address with your model server’s address, without /v1. Leave this terminal running. Stop it with Ctrl-C when your agent is idle; restart the same command with the same state directory to reuse saved notes and archives. Your agent still needs to preserve and resend its full conversation.

Docker instead (Linux)

Build from the released source archive, then run the proxy with a persistent named volume. Linux host networking lets 127.0.0.1:8000 reach a model server running on the host. The explicit bind address keeps this example local to your machine.

R=https://github.com/steveseguin/b70-optimization-lab/releases/download/ctxkeeper-v1.1.0
docker build -t ctxkeeper:1.1.0 "$R/ctxkeeper-1.1.0.tar.gz"
docker run --rm -it --name ctxkeeper --network host \
  -v ctxkeeper-state:/state ctxkeeper:1.1.0 \
  --host 127.0.0.1 --recipe agent --upstream http://127.0.0.1:8000

Keep it running while your agent works. Ctrl-C stops the proxy; the named volume survives --rm. Run the same command again to reuse it. Docker Desktop networking differs; use a reachable host address for your setup. The demo below runs on your host and needs Python 3.10 or newer.

Check the connection, then run the demo

In a second terminal, check that the proxy can reach the server and list its model IDs:

curl --fail --show-error http://127.0.0.1:18200/v1/models
curl --fail --show-error http://127.0.0.1:18200/ctxkeeper/status

The model list checks reachability; it does not test note quality. The status may be empty before the first conversation. The demo grows a conversation beyond the working view and checks a codename, a changing budget and a standing rule at the end:

R=https://github.com/steveseguin/b70-optimization-lab/releases/download/ctxkeeper-v1.1.0
curl --fail --location --output long_chat.py "$R/long_chat.py"
python3 long_chat.py --base-url http://127.0.0.1:18200/v1

The demo uses the first model returned by /v1/models; add --model your-model-id to choose another. It prints its answers and a score. Test your own workload before relying on the notes.

Connect your agent or app

Set its OpenAI-compatible base URL to http://127.0.0.1:18200/v1, including /v1. Set the model to an ID from the model list above. If the client requires an API key, use unused for this local setup.

Stable 1.1.0 requires an upstream that accepts these managed calls without an API key. It does not forward the client’s Authorization header for Chat Completions and has no upstream-key option. Setting a real key in your agent will not authenticate those calls. ctxkeeper itself has no login.

  • Use Chat Completions (/v1/chat/completions). Other endpoints, including Responses, pass through without context management.
  • Send the whole conversation each time. Turn off the agent’s own history trimming and summarizing. If earlier messages disappear or change, ctxkeeper may treat it as a different conversation.
  • Request one reply at a time (n=1). Streaming is accepted, but the answer arrives in one piece at the end.
Python client example

The optional OpenAI client library is a separate install: python -m pip install openai. Replace the model ID before running:

from openai import OpenAI
client = OpenAI(base_url="http://127.0.0.1:18200/v1", api_key="unused")
history = [{"role": "user", "content": "Remember: our project is called Cedar."}]
reply = client.chat.completions.create(model="your-model-id", messages=history)
print(reply.choices[0].message.content)
history.append(reply.choices[0].message.model_dump(exclude_none=True))
# Append each new user message and send the whole history on the next call.

For new instructions inside tool results, such as tickets or files, --recite-when '(?m)^TICKET \d+' repeats recorded rules after matching messages. The release repair test kept its rules without this option; the fastest repair runs used it. Neither setting guarantees rule compliance.

Limits

  • Measured on one model family and one machine, with the model keeping its own notes. A small Gemma demo also passed; other models’ task quality has not been measured here. A separate, smaller model as the keeper did worse: LFM2.5-24B-A2B on a second card kept the house rules on 20 of 40 bugs and answered 19 of 39 on the 240K test, and it was slower, because it reads every turn afresh instead of from the main model’s cache.
  • The notes are written by the model, so they can be wrong. The latest development seed had one wrong counter line across 8,813 saved counter lines; an earlier run kept one wrong value for 118 notes versions. On the million-token test, one of 1,435 counter lines was wrong. The originals stay searchable, but nothing forces the model to look. In the agent test one notes line wrongly said seven questions had never been asked, and the agent deleted the answers it had already written.
  • No login, and everything is stored as plain text on the machine running it. The commands above bind only to the local machine. The Docker image’s own default binds to all interfaces, so keep the explicit --host 127.0.0.1 in the host-network command.
  • The opening instructions are always kept, so they must fit well inside the working view.
