ctxkeeper

Keep your agent working when its conversation outgrows the model's context window. Free, public-domain proxy; install with pip or Docker.

Free · public domain · Python 3.10+, standard library only

A small proxy between your agent and any OpenAI-compatible model server. Your agent keeps its whole history; the model sees a short, current view — notes it maintains, the opening instructions, the newest turns. Everything older is archived word for word, searchable through a recall tool the proxy answers itself.

Install and run

Point your agent at http://127.0.0.1:18200/v1 instead of the model server. Keep the client’s full conversation history, as described below.

pip

python3 -m venv .venv-ctxkeeper
. .venv-ctxkeeper/bin/activate
python -m pip install ctxkeeper

ctxkeeper --recipe qwen \
  --upstream http://127.0.0.1:8080

Docker

docker build -t ctxkeeper:1.2.0 \
  "https://github.com/steveseguin/b70-optimization-lab/releases/download/ctxkeeper-v1.2.0/ctxkeeper-1.2.0.tar.gz"

docker run --rm --network host \
  -v ctxkeeper-state:/state \
  ctxkeeper:1.2.0 --host 127.0.0.1 --recipe qwen \
  --upstream http://127.0.0.1:8080

Source, issues and the full guide: github.com/skindeepai/ctxkeeper. Or take just the two files — ctxkeeper.py and notesdelta.py — from the release page, which lists every file’s SHA-256. The upstream must accept managed calls without an API key (client Authorization headers are not forwarded); keep the proxy on localhost or a trusted network. The full guide covers every option, the status page and the tests.

Measured, not promised

A 32K working view kept up with a full 262K context — and finished sooner. On a separate million-token memory task, it answered more questions correctly than a 200K sliding window, in less time. The older history stayed on disk, available through recall.

Which model do I need?

  • Measured on Qwen3.8-27B (FP8 on two B70 cards). One card is enough: the repair task scored the same in 21 minutes.
  • A quick check on a second family, Gemma 4 26B (Q8, llama.cpp), passed the demo 4 of 4. Other models need checking with your task: they must call tools reliably, keep the notes format, and fit the working view plus server overhead.
  • Let the model keep its own notes. A separate smaller keeper model was worse and slower (19 of 39 vs 39/39 on the 240K test): it reads every turn afresh instead of reusing the main model’s cache.

Connect your agent

Start with Pi or OpenCode and a local model server. Both were tested through ctxkeeper. Version 1.2.0 manages /v1/chat/completions; the client must keep sending its full conversation.

Client or modelConnection in 1.2.0
PiTested with a local model. Add a Chat Completions provider and disable compaction.
OpenCode 1.xTested with a local model. Use its OpenAI-compatible provider and disable compaction and pruning.
OpenAI SDK / custom clientChat Completions supported. Keep the message history and handle tool calls.
CodexResponses API passes through; no ctxkeeper memory management on that path.
Claude CodeUses a different API. Needs an additional protocol adapter; not tested.
Grok via xAI APIChat Completions protocol fits, but needs an upstream gateway to supply the API key; not tested.

First start your tool-capable model server, then run ctxkeeper using the command above. Use --recipe qwen for the tested Qwen/vLLM setup, or --recipe agent for other compatible models. Find the model ID with:

curl http://127.0.0.1:18200/v1/models

Replace every YOUR_MODEL_ID below with the exact ID the server returns. Merge these examples into existing configuration files. The large client history ceiling lets the agent retain old turns; ctxkeeper still sends a 32K working view. It does not ask you to allocate a ten-million-token model context.

Pi — configuration and launch command

Add a provider in ~/.pi/agent/models.json:

{
  "providers": {
    "ctxkeeper": {
      "baseUrl": "http://127.0.0.1:18200/v1",
      "api": "openai-completions",
      "apiKey": "unused",
      "models": [{
        "id": "YOUR_MODEL_ID",
        "name": "Local model via ctxkeeper",
        "input": ["text"],
        "contextWindow": 10000000,
        "maxTokens": 4096
      }]
    }
  }
}

In ~/.pi/agent/settings.json, disable automatic compaction:

{
  "compaction": { "enabled": false }
}
pi --provider ctxkeeper --model YOUR_MODEL_ID

Avoid manual /compact during that conversation too. Tested with Pi 1.2.0; its result and the notes failure are included in the agent comparison. See Pi’s custom endpoint guide and settings reference.

OpenCode 1.x — configuration and launch command

Add this to your project’s opencode.json. This is the 1.x configuration format, tested with 1.19.0.

{
  "$schema": "https://opencode.ai/config.json",
  "model": "ctxkeeper/YOUR_MODEL_ID",
  "small_model": "ctxkeeper/YOUR_MODEL_ID",
  "provider": {
    "ctxkeeper": {
      "npm": "@ai-sdk/openai-compatible",
      "name": "ctxkeeper",
      "options": {
        "baseURL": "http://127.0.0.1:18200/v1",
        "apiKey": "unused"
      },
      "models": {
        "YOUR_MODEL_ID": {
          "name": "Local model via ctxkeeper",
          "tool_call": true,
          "limit": { "context": 10000000, "output": 4096 }
        }
      }
    }
  },
  "compaction": { "auto": false, "prune": false }
}
opencode --model ctxkeeper/YOUR_MODEL_ID

Select @ai-sdk/openai-compatible so requests use Chat Completions. The OpenAI provider can use Responses, which ctxkeeper passes through without managing context. See OpenCode’s provider guide and configuration reference. Check the format before adapting this to a new major version.

OpenAI SDK and other Chat Completions clients

Use base URL http://127.0.0.1:18200/v1, model YOUR_MODEL_ID, and the placeholder API key unused if your client requires a key. Call chat.completions.create, keep the full message list, and request one reply at a time (n=1). The SDK example covers plain replies, tool calls and streaming. Streaming is accepted, but each answer arrives in one piece at the end.

For other clients, choose a custom OpenAI-compatible Chat Completions provider, set the same base URL, and disable history trimming and summarizing. Cline, Goose, mini-swe-agent and others were also tested below; the exact provider controls depend on the client version.

Codex — why a base URL is not enough yet

Current Codex custom providers use the Responses API. ctxkeeper 1.2.0 forwards that endpoint without making notes, cutting context or serving recall. Pointing Codex at port 18200 therefore does not enable these features.

A managed connection needs Responses support in ctxkeeper or a tested Responses-to-Chat-Completions adapter. Neither is included in this release. For a working local-model setup today, use the Pi or OpenCode configuration above. See the Codex configuration reference.

Claude Code — a protocol adapter is required

Claude Code’s custom gateway uses the Anthropic Messages format, which ctxkeeper 1.2.0 does not manage. Setting ANTHROPIC_BASE_URL to ctxkeeper alone will not add its memory features.

A possible integration would need a Messages-to-Chat-Completions adapter before ctxkeeper and an upstream gateway that authenticates with the model provider. That combination has not been tested here. Follow the Claude Code gateway compatibility guide when evaluating an adapter; tool calls, thinking and streaming must survive the conversion. The Claude web app is not a configurable Chat Completions client.

Grok and other hosted models — supply credentials upstream

Grok is a model you can use through the xAI API. Its Chat Completions endpoint uses the right protocol, but requires an API key. ctxkeeper 1.2.0 does not forward the client’s Authorization header or provide an upstream API-key setting.

The route to evaluate is Pi or OpenCode → ctxkeeper → a local gateway holding your xAI key → xAI. Configure that gateway to expose Chat Completions locally, point --upstream at it, and select its Grok model alias in the client. Keep the key in the gateway; apiKey: "unused" in the examples is only a client placeholder.

This hosted route is not tested or packaged here. A Grok website or app subscription is not the API connection described above.

Check the connection and keep conversations separate 
curl http://127.0.0.1:18200/ctxkeeper/status

Check the status while using the client. Notes and cuts start once the conversation grows beyond the working budget; a short successful reply alone does not demonstrate memory management.

If your client supports custom headers, send a unique X-Ctx-Session value per conversation and keep it on every call, including after a restart. Otherwise ctxkeeper identifies conversations by their model and opening messages; identical openings can collide. If earlier messages disappear or change, it may treat the history as a new conversation.

For new instructions inside tool results, such as tickets or files, --recite-when '(?m)^TICKET \d+' repeats recorded rules after matching messages.

Limits, stated

  • The notes are written by the model, so they can be wrong. The originals stay archived and searchable, but nothing forces the model to look. In one agent test a wrong notes line said seven questions had never been asked, and the agent deleted answers it had already written.
  • Silent arithmetic slips exist. Two 2M-seed answers mis-added while the notes held the right value; the arithmetic check only catches wrong working it can see.
  • No login; state is plain text on the machine running it. Bind to localhost (the commands above do). The Docker default binds to all interfaces — keep the explicit --host 127.0.0.1 if you change the run command.
  • The opening instructions are always kept, so they must fit well inside the working view (default 32,768 tokens).
