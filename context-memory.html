Can disk replace GPU memory?

Text files, saved numerical state and active offloading solve different problems.

No: a GPU with only a few kilobytes free cannot gain a full 200K-token active context simply by saving it to disk. The model needs working space to compute, and its numerical context is much larger than the text. A system designed to offload computation or cache blocks can trade speed for capacity, but it still needs buffers and data transfers.

Three different things people call “context on disk”

1. Save text and records

Keep documents or a state table in files. Read selected parts when needed.

Measured here. The ledger finished in 1.9 minutes with under 9K active context.

Files and retrieval

2. Park an inactive cache

Save the model’s numerical state between sessions, then restore it before use.

Proposed here. Pay save/restore time; the active state still needs somewhere to run.

How parking differs

3. Stream the active cache

Move cache blocks during generation because they cannot all stay in GPU memory.

Not measured here. Repeated transfers can become the bottleneck.

Why speed changes

Why 200K tokens need gigabytes

The text is converted into arrays of numbers that let attention use earlier tokens. For the target model’s 16 full-attention layers with a 16-bit key/value cache, those arrays grow by 64 KiB per token across both GPUs.

Active tokensAttention-cache payload across both GPUs
8,1920.50 GiB
32,7682.00 GiB
60,0003.66 GiB
120,0007.32 GiB
200,00012.21 GiB
262,14416.00 GiB

Calculated attention KV payload only. Model weights, recurrent state, drafting, checkpoints, allocation padding and temporary workspace require additional memory. This is specific to this model and precision, not a universal LLM formula.

A 200K-token prompt therefore needs about 12.2 GiB of attention cache, roughly 6.1 GiB per GPU when evenly split across two. A few spare kilobytes are insufficient even before other working memory is counted.

200 KB is not 200K tokens. KB measures file bytes. Tokens are pieces of text counted by the model’s tokenizer. Their relationship depends on the text, language and tokenizer; count the tokens before estimating the cache.

Does parking the cache avoid a decode penalty?

If the complete required state is restored into the same active memory layout before generation, the design need not add disk traffic to each subsequent token. But saving and restoring takes time, and that design cannot help an active state that still does not fit.

A byte-preserving snapshot can retain the numerical values. Correct continuation also requires compatible model weights, positions, recurrent state and runtime metadata. A model or runtime change can make a saved cache unusable. The lab proposed this path; it did not publish a completed save/restore benchmark.

What happens if the GPU must keep fetching from disk?

Full attention needs the earlier keys and values during generation. If almost the entire 200K cache must be read from storage for each ordinary next-token pass, approximately 13.1 GB must move per pass. Fast storage is still far from a free replacement for local GPU memory.

Assumed sustained storage read rateTime to move the 200K cache once
1 GB/sAt least 13.11 seconds
5 GB/sAt least 2.62 seconds
10 GB/sAt least 1.31 seconds

Illustrative lower bounds: 13.1072 GB divided by the assumed sustained read rate. These are transfer times, not measured model speeds. They exclude computation and any additional unoverlapped upload. Keeping part of the cache resident, overlapping work, or accepting multiple draft tokens per pass changes the calculation.

That is why this research does not establish a disk-streamed decode rate. The measured roughly 35 tokens/s at 200K used an in-memory cache. A proposed disk path needs its own full-task, speed and correctness tests.

What can a memory-constrained machine do?

Use a smaller active context with files or retrieval when the task allows it. If all the text must be active at once, the options involve enough memory, a smaller model or cache representation, or an engine that explicitly supports offloading. Saving a transcript alone does not change the model’s 262,144-position limit.

Calculation and original sources

16 attention layers × 2 arrays (K and V) × 4 KV heads × 256 values per head × 2 bytes = 65,536 bytes per token. The recurrent layers add state separately.
