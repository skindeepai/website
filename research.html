Research FAQ

What the experiments show, how the methods work, and what is still untested.

Learning preferences

Can it learn what I like?

The demo learns patterns in your ratings and uses them to score or adjust drawings. Its calculations and simple made-up preferences have been tested; we have not yet shown that people prefer its suggestions.

How learning works · Preference tests

Does choosing examples carefully save ratings?

Not consistently in our tests. The demo’s mix of likely likes, uncertain examples and random examples performed worse with noisy ratings than random sampling; selecting uncertain examples did better on the simple test rules.

Actual demo sampler: comparison and learning curves

Can it learn different tastes or changing moods?

A single linear model struggles with separated tastes. A nonlinear feature model helped in a synthetic test; keeping separate models for explicitly named contexts also helped in a small alternating-context test. Neither demonstrates learning a person’s changing moods.

More than one taste · Context and retention tests

Does a higher model score mean a better suggestion?

No. A model can confidently prefer the wrong thing. We tested selection from the same candidate pool and retained cases where maximizing the score disagrees with the known preference; a person’s new rating is still the real check.

Decisions and speed

Does the model need to write an answer?

No. A small classifier can read its internal numbers and return a label directly. Returning a number instead of one trained token did not, by itself, show a reliable speed advantage.

Decisions without text · Matched output test · Try real moderation messages in your browser · Try the small trained classifier · Search documents locally · Compare a real shared model on your device

How early can it stop, and does that save time?

A shared four-layer BERT model can answer after layer 2. On 500 unused messages, its frozen rule preserved every full-depth decision while proposing 400 early exits, or 40% fewer transformer blocks. Actual browser execution also works. Only 18 new test messages were toxic, so rare-error reliability remains uncertain.

500-message fresh validation · Run the shared model yourself · Compare early, middle and late layers · Earlier Qwen stopping results

Can it go faster without changing its answers?

On 100 tested messages, reusing the fixed instructions cut time by 37.9% with identical decisions. Processing messages in groups of four cut queue time by 9.7%. Both still use all 24 layers; these checks do not establish identical behavior on every possible input.

Reuse the instructions · Process a queue together

Would a tiny model with a larger fallback be simpler?

The original pilot roughly halved time, but introduced a toxic-message miss. On 100 new messages, a stricter fallback matched Qwen’s decisions while avoiding Qwen only twice; its measured time saving was less than 1%.

How the cascade works · Its exact test results · New messages and stricter fallback

Does it follow changing rules or understand a live conversation?

Not reliably in the tests so far: opposite rules exposed failures even at full depth. We have not tested these decision classifiers on live conversations with audio or video context.

Clicks and actions

Can it return a click location directly?

Yes, a pointer model can return a location without writing coordinates as text. It found 25/30 targets in the first study, but only 8/25 on a harder new benchmark. A confidence cutoff withheld all 25 infeasible requests there, while also withholding 21 valid ones and still allowing two wrong clicks.

Harder screenshots and infeasible requests · Click-target results · Inspect real screenshot results · Run a small image-to-action model

Can those decisions finish a task?

A separate small grid model completed 7 of 10 mazes after more training and a rule against wall moves. That is not a completed GUI task: the screenshot tests return points and do not execute clicks.

Longer context

Can disk make up for limited video memory, so a card with room for 16K of context works with 200K?

Two different things. Measured, at the application level: yes. With files allowed, the model kept its working data on disk and its context under 9K on a 121K-token task, with every answer right, 14 to 22 times faster than keeping the data in context. Nothing is lost because the raw data stays on disk. This works when code or search does the reading; when the model itself must understand raw text, that text has to pass through the card at some point. Estimated from measurements, not built, at the engine level: the model’s cache is 64 KiB per token, so 200K of context is about 13 GB. Every written token would have to pass the whole cache through the card. This drive reads 12.7 GB/s (measured) and uploads run at roughly 9-16 GB/s, so one step takes a little over a second: roughly 3-4 tokens a second against about 35 with the cache in video memory, and several times slower on an ordinary drive. Reading a 200K prompt would stream about 1.5 TB, roughly doubling the two-minute read. The arithmetic would run in pieces, so results would be repeatable but not bit-identical to the in-memory path. Not built: parking a whole conversation’s cache on disk (about 13 GB for 200K) and restoring it in seconds instead of re-reading for two minutes; that would be byte-for-byte lossless.

The disk arithmetic · Files on the 121K task · Working past the context limit

Can the context be edited surgically, as in the paper, to be unlimited, without plain trimming or a full summary?

Measured so far: yes in mechanism, with caveats. The model’s own surgical edits lost nothing: it kept a small state table, folded each batch in by code and deleted the raw batch. The paper’s harness lost data through its own rollback. An exact prefix cache means an edit costs only re-reading what follows the edit point, resuming from a kept state before it, while staying identical to a cold read. The decisive test, a 480K stream (bigger than the window) at a 32K budget, is running. What stays true: an edit deletes text from the model’s view. Unless the removed text is saved somewhere it is gone, so “unlimited” means an unlimited length of work, not unlimited detail at once.

Comparison and losses · Method and raw data · Exact cache

How fast is it all, and how much quality is lost?

Measured: reading slows from 3,280 tokens a second at 8K to 1,550 at 250K, and writing from 127 to 26. With the exact cache a question over a cached 200K context starts in 2 s instead of 114 s; the first read is 14-27% slower. Summarising took 41 minutes, keeping everything 26, and keeping the data in files 1.9. Recall is exact at 60K; from 120K to 250K about 1 look-up in 40 returns a look-alike neighbour, and nothing is invented. Disk is not the limit (the drive reads 12.7 GB/s); the model’s writing speed is. Long agent tasks: one task family, one or two seeds, up to 121K so far; longer ones are running. Not measured: several users sharing the cache, other task families, hard decisions where thinking changes the answer.

How is this different from an updated plan file, the way the B70 lab is run?

Measured: the same idea at a different layer, and the results favour it. A plan file is state kept outside the model’s context, rewritten as work proceeds, with the raw evidence in other files; it survives a context reset and a new session. Self-editing edits the running transcript in place, so a reset is not needed. In the measurements the winning pattern was exactly the plan-file pattern: state and data on disk, small context. In-context editing is the tool for keeping the record of the agent’s own steps small between plan updates. Differences: a plan file is only as good as what was written into it (what was not written down is lost at the reset), and it costs a re-read at the start of each session; in-context state is always in view but shrinks the room for everything else and slows writing. The improved agent tested here pins a small state block that the harness checks: a plan file kept inside the context.

Can a small CPU-side cleaner or classifier turn 32K into 100K?

Measured: no. On 5.0M tokens of real agent sessions, strict no-loss cleaning frees 1.8% and moving large tool outputs to disk 7.5%. The model’s re-sent old thinking is about 10% of a typical call (up to 56%), but dropping it blindly made one run get stuck.

Scope and limits

Can preferences stay within hard requirements?

Explicit bounds can prevent a known forbidden edit; new conflict cases check that mechanism. A high preference score is not a safety guarantee, and personalized instruction-following has not been validated.

Constraint-conflict checks

Are the ratings and representations private?

The browser demo keeps its ratings on your device. That does not prove an encoded image hides private information; we have not run a reconstruction or privacy-attack study.

Local preference demo

Has this been tested on real generators, music or other applications?

Not in the current experiments. Generator transfer, music, feeds, mutual preferences and engineering designs are proposed applications; validating them needs task data, appropriate models and, where relevant, participating users.

Original project and current scope

Will the results hold on another model or device?

A separate implementation replay reproduced saved decisions and layer stopping, including a published runtime version. We have CPU timings and a full-depth browser demo, but no matched GPU/NPU comparison or evidence that the trained classifiers transfer to another model.
