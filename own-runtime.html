Our own inference runtime

A custom inference engine for Qwen3.8 hybrid models on Intel Arc Pro B70 cards, built for speed and provably identical output.

Research engine · Intel Arc Pro B70 · measured, with receipts

Most local models run on a general-purpose engine. We built our own for one model family: a small inference engine for Qwen3.8 hybrid models on Intel Arc Pro B70 cards. It exists to prove two things at once — speed, and output that is provably identical to a reference run, byte for byte. A run that cannot prove itself does not get published.

  • Fast. 58.6 tokens a second on two cards, 31.8 on one, on the model we run most; on 2026-10-22 the record runs reached 60.7 on two cards and 35.9 on one.
  • Exact. Every published output is checked against an oracle or an independent repeat run, with receipts kept.
  • Resumable. A session saved mid-answer was restored in a fresh process and finished the answer byte for byte; later the same day a saved session took a new question after restore and answered exactly as a fresh run would.
  • Open about gaps. Caps and pending checks are stated on the page, not hidden in footnotes.

What it is

Qwen3.8 Flash-Next is a hybrid model: 48 layers, of which 36 use gated delta net (a linear-attention design) and 12 use full attention, plus a 512-expert mixture layer and an early composite layer. General engines run it through generic kernels. This engine is designed around that exact structure: a per-layer plan, a resident cache for the experts, and snapshot banks for the state.

It is a research engine, not a shipped product. There is nothing to download as a finished program; the reproducible artifacts are the recipe pages and lab records linked below.

Session swap: park the computation, not just the text

Ordinarily, returning to an old conversation means the model reads the whole prompt again. Because we own the engine, it can do something frontends cannot: save a session’s computed state to disk, restore it later, and continue without re-reading the prompt. The ideas behind this are described on our cache parking and cache offload pages.

The first restart-and-continue test passed on 2026-10-22. On one card, a request ran to token 256 and was saved to disk (1.10 s, 68.8 MB). Two separate fresh processes each restored it and wrote 128 more tokens. Both merged outputs equal an uninterrupted run of the same prompt, byte for byte, and the two restores are identical to each other. Restoring took 0.46 s; re-reading the same prompt from cold took 36.75 s.

Later on 2026-10-22 the next step passed too. A second engine revision can take a saved conversation, add the next question, and answer; on one card the answer equaled a fresh run of the whole conversation, byte for byte. It can also save again after a restore, and resuming from that second save matched as well. Refusals happen before anything touches the card: a tampered side file, a mismatched prefix or tokenizer, a wrong delete target.

Saved sessions are now labeled “qualified, one card”. A third build the same day writes that label, with a record of which test qualified which operation, and still reads the earlier experimental files.

Two-card sessions passed the same tests on 2026-10-22. On the two-card record engine, a session was saved with both cards' state, including the draft model's cache, and a fresh pair of processes restored it and continued; adding a question, saving again and resuming all matched a one-shot run, and the re-saved state was byte-identical on both cards. Two-card saves are labeled experimental until a further build writes the qualified label. Not yet: ctxkeeper does not call these operations. The written design contract — save, inspect, restore and delete, with compatibility checks and prefix-plus-delta rules — is what the integration is built against.

How it fits with ctxkeeper

ctxkeeper keeps a long conversation durable from the outside: notes, a searchable archive and a small working view, working with any model server. The own runtime is the other half: the checkpoint engine inside the server that can save and restore the actual computation. ctxkeeper decides what a session needs to remember; the engine provides the how for instant resume. The session-swap contract above is what the ctxkeeper integration is being built against.
