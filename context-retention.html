Remembering what was dropped

An archive of dropped text with a search tool answered questions about the past as well as summarising, in a quarter of the time.

The goal: when an agent has to make room, lose less than summarising does, and spend less time doing it. Moving dropped text to a searchable archive answered every question, including those about text it had dropped, in a quarter of the summariser’s time.

The test

The 119K-token narrative reading task, with twelve extra questions asked only at the end: values that were later overwritten, and small details in the text. 36 questions in all. Every approach had a 32K working budget except keep-everything, which used the full window.

What it showed

  • The archive beat summarising on time and writing, at equal correctness. Both answered 36 of 36. The archive agent took 6.1 min and wrote 14K tokens; the summariser took 26 min and wrote 121K tokens.
  • A running table alone cannot answer about the past. It keeps only current values, so questions about overwritten values and details went blank or wrong: 25 of 36.
  • The plain files agent collapsed because it has no guards. It spent its 32K budget thinking before it had finished reading and was stopped: 3 of 36. The same agent got every answer on the version without the extra questions.

How the archive works

  1. When the agent drops a batch from its working context, the batch goes word for word to an archive the model can read but not change.
  2. A recall search tool finds passages in that archive.
  3. Recalled text counts against the 32K budget like any other tool output.
  4. The grader voids the run if any other file holds stream data, so the archive is the only memory outside the context.

Nothing is deleted, only moved out of view. In this run the agent searched the archive 12 times. How summaries work · Why files helped on the ledger.

On an outside benchmark

The same ranking held on a public memory benchmark, with the archive again the cheaper of the two methods that manage context. LongMemEval_S (MIT licence), 56 of the 500 questions: 8 per question type, each with about 110K tokens of chat history. The model must answer one question about a long chat history: a fact the user mentioned once, something the assistant said, a preference, a date to work out, a fact that was later updated, or a question the history does not answer, where the right reply is to say so. Every approach ran with the same 27B model on Two Intel Arc Pro B70, 65,536-token window.

3 questions only the archive got right, 2 only summarising got right, and 1 neither. That is a tie on accuracy at this sample size. The archive spent a third of the time and wrote a sixth of the tokens. A small pilot of seven questions had put summarising ahead; it did not hold up, which is what the larger run was for.

Reading the whole history in one call is still the best answer whenever it fits the window. Where the archive falls short of it: questions the history cannot answer, 1 of 8 against 4 of 8 for whole-history reading: it answers when the history does not say; and preferences, 4 of 8 against 5 of 8. Teaching the note-taker to record what was not said is the next step.

The judge: Qwen3.8-27B FP8 on the lab host, using the benchmark's official judge prompts. The benchmark's published scores use GPT-4o as judge, so these numbers are not directly comparable with published ones. The run was stopped once by the host memory guard at 52 of 56 archive trials and resumed; finished trials were kept, no GPU fault. Lab note · Per-question verdicts and scripts (2026-10-08).

Limits

The synthetic retention test above is one seed and one task family. The outside benchmark adds 56 questions from a second source with a different judge; the published scores for that benchmark use a different judge model, so compare the approaches with each other here, not with published leaderboards. Summarising also got every answer on the synthetic test: with thinking on, its summaries kept the old values. Its cost was time and writing, not accuracy.
